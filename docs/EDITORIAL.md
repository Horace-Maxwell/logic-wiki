# 双语编辑维护

新增或修改内容时，先固定来源和主张，再执行本项目的中英 Humanizer 编辑。检查量词、否定、条件、证据强度和数值，最后检查案例边界与页面。结构化目录方便维护；它不是自动判定谬误的算法。

## 保存实际完成的审校

```sh
npm run review -- --worksheet /tmp/logic-review.json
```

命令生成未完成的工作表。删去本次未复核的记录，只为实际检查的知识单元填写执行者、完成阶段、具体发现与处理说明。`candidateHash` 必须对应审校时的内容；不能在未阅读新版内容时替换哈希。`completed` 中的阶段为：

1. `source-check`：核对事实、实际查阅材料与论证结构。
2. `zh-edit`：中文 Humanizer 编辑。
3. `zh-semantic-check`：复核中文编辑没有改变含义。
4. `en-edit`：英文撰写与 Humanizer 编辑。
5. `bilingual-check`：逐项比较两种语言的事实、范围和强度。
6. `exercise-and-render-check`：检查案例、答案、公式和输出页面。

这组阶段把来源核查后的写作纳入相应语言编辑阶段。`executor.type` 如实填写 `agent` 或 `human`；代理执行者使用具体名称，不写“专家审核”。`unresolved` 有未解决问题时不能登记完成。

```sh
npm run review -- --record /tmp/logic-review.json
npm run content:check
```

登记命令只保存审校声明，不会替你执行编辑。中文、英文和完整单元分别绑定哈希；英文还绑定中文依据。相关来源、术语表和规则改变时，旧记录失效。页面组件、MDX、导航和共享文案由 `site-copy` 记录覆盖。

## 文风提示与保护范围

聊天残留、未完成占位内容会阻止构建。空泛拔高与套话产生需要处理的提示。修改文本后重新复核；若确实是在引用原话或讨论某种表达，可记录例外：

```json
{
  "rule": "placeholder",
  "path": "具体受影响字段",
  "type": "quoted-or-discussed",
  "reason": "指明被讨论的短语及其教学用途；不是遗漏的正文。"
}
```

例外绑定当前内容版本，不会为后续修改自动放行。公式、引用原文、链接、文献与专名不做同义词替换。保留有教学作用的对照、列表和统一章节。自然程度与翻译等值依靠编辑判断，不使用“AI 分数”作为通过标准。

## 来源和分类

在来源登记中记录作者、版本、章节或定位、日期、链接、许可及查阅范围。未查阅正文的书籍只能作为延伸书目，不能写成正文事实的依据。原始材料和本站分析分开；监管指控不改写成已经独立证明的事实。

别名归入同一 ID。例如 converse accident 归入草率概括，不再单独计数。上下位类型仍可能有各自教学词条；“那你们呢”与“你也一样”等重叠现象不被描述成互斥分类。新增词条先检查别名、定义边界和已有案例。

## 更新规则

更新 Humanizer 时先下载到临时目录，对比规则与许可证，再更新固定提交和文件哈希。重新运行回归样例并编辑受影响正文。构建不会调用 `scripts/vendor-humanizer.py`，也不会自动拉取上游新版。

## 练习身份与版本

题目、选项和答案使用稳定 ID。现有 100 个错误词条均使用单独编写的情境题，题目声明自己的 ID，不能按数组下标命名。早期复用案例的 `-inference` 与 `-control` 仅作为旧数据兼容规则，不用于现版题库。选项 ID 在中英文间共享；展示顺序可以改变。

题目版本覆盖两种语言的题干、解析、选项和可接受答案。任一内容改变后，该题的旧作答不再显示；其他未改题目保留。多种解释都可接受时，逐项填写 `feedback`，写明各解释成立的条件。测试应同时检查顺序调整、语言切换、内容变更和无效存储。

仅调整数据结构时，也必须比较新旧内容与已有审校范围。保留旧记录、迁移依据和新增验证结果；不能把结构迁移记作重新阅读了所有文献。审校工具自身变更会使记录失效，重新登记前应核查规则差异及其对既有审校的影响。
